# E. 质量验证

这是本 skill 的核心。其他四个维度在判断内容好坏；这一维判断**你有没有资格说「做完了」**。

## 四态定义

任何验证结论必须落入其中一态，不存在第五种。

| 状态 | 含义 | 报告要求 |
|---|---|---|
| **Passed** | 实际执行了验证且通过 | 写出完整命令 + 关键输出行 |
| **Failed** | 实际执行了验证且失败 | 写出完整命令 + 真实错误输出 |
| **Blocked** | 想验证但环境/依赖不允许 | 写出卡点：缺什么环境、什么权限、什么依赖 |
| **Not Run** | 没做验证 | 写出原因：时间、范围外、用户没要求 |

## 不允许的表述

这些表述出现即视为验证造假：

- 没给命令和输出就断言功能正常
- 用类型检查结论代替功能验证
- 把 Failed 描述成「基本可用」
- 把 Not Run 描述成「已实现」

`类型检查通过` 只能证明类型正确。`构建通过` 只能证明能构建。两者都不是功能验证。

## 按交付物类型的验证层级

| 交付物 | 最低验证 | 更强的验证 |
|---|---|---|
| 函数/模块 | 单元测试跑通 | 边界值与错误路径覆盖 |
| CLI | 实际执行，观察输出 | 异常输入下的行为 |
| 服务 | 启动 + 请求一次 | 负载、失败恢复 |
| UI | 渲染截图 + 交互一次 | 多视口、多状态 |
| 文档 | 操作性声明逐条对照同树实现（`file:line` 或帮助输出）；可安全执行的命令实际执行 | 示例在干净环境复现；多语言镜像逐项比对 |
| 数据/脚本 | 用真实输入跑一次 | 大输入、异常输入 |
| 视觉生成 | 渲染后目视检查 | 实际尺寸/速度下检查 |

表格本身不构成验证。每一项都要附实际命令或渲染证据。

## 报告格式

没有验证的交付必须显式列出：

```
## 验证

- Passed：`pytest tests/test_x.py -v` → 12 passed
- Failed：`npm run build` → error TS2345 at src/a.ts:42（未修复）
- Blocked：端到端测试，需要设备未连接
- Not Run：浏览器兼容性，本轮未做
```

## 常见的自我欺骗

**测试通过 ≠ 功能正确。** 测试覆盖的是你想到的路径。用户遇到的可能是没想到的那条。

**跑过一次 ≠ 跑对过。** 要看输出内容，不只看退出码。

**局部通过 ≠ 全部通过。** 只跑了相关测试就写「测试通过」属于夸大。写「跑了 X 测试，Y 未跑」。

**修好一处 ≠ 问题解决。** 症状消失不等于根因消除。根因未定位时，明确说是症状级修复。

**文档写了 ≠ 实现存在。** 从上游、旧版本或记忆移植的命令行，可能在同树代码里没有对应实现。文档的验证按声明逐条成立，不是按文件成立——一行错的文档让整个文件处于 Failed。

**Passed 有范围。** 「在 Linux / Python 3.14 下通过」不等于跨平台通过。

**验证记录也是声明。** 「实测输出」里的每一行都会被复核。写可复现的命令、条件与精确输出；印象性描述（「渲染为空白」「快了很多」）无法复现，写出来就是新的未验证声明。

## 与其他维度的关系

A–D 的审查结论本身也需要验证状态。例如「视觉无穿帮」只有在渲染后检查过才能写 Passed；只读了 SVG 源码，那是 Not Run。
