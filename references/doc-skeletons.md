# 其他文档骨架

## 设计文档

1. 要解决的问题（一句话 + 现状）
2. 目标与非目标
3. 方案：关键数据结构、接口、流程
4. 取舍：为什么不用另外两条路
5. 风险与回滚

非目标必须写，否则范围无边界。

## API 文档

每个接口固定顺序，字段解释一行一个：

- 签名：`POST /v1/items`
- 参数：名称 / 类型 / 必填 / 默认值 / 说明（表格）
- 返回：字段 + 类型 + 示例 JSON
- 错误：code / 触发条件 / 处理建议
- 示例：一条 curl，真实值

不要写「本接口用于…」这种开头，参数表本身就是说明。

## 使用指南

按任务组织，不按功能组织。每节形如：场景一句话 → 命令 → 预期输出 → 常见报错。

## 变更日志

```
## [1.2.0] - 2026-05-01
### 破坏性变更
- 移除 `--old-flag`，改用 `--new-flag`
### 新增
- 支持 …
### 修复
- 修复 … 时崩溃
```

只写对使用者有影响的改动。不写「优化了代码结构」「提升了性能」这种没有数字的条目。
