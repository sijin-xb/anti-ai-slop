# B. 反过度工程

审查对象：代码、架构、配置、目录结构、依赖清单、重构方案。

## 判定原则

复杂度必须由一个真实存在的约束支付：性能、安全、并发、可测试性、明确的未来需求。说不出约束的复杂度就是成本。三行相似代码好过一个过早的抽象。

## 检查清单

**抽象**
- 接口是否只有一个实现？只有一个实现时，接口是否只是多了一层跳转？
- 工厂、策略、观察者、建造者这些模式是否被用来解决一个 if/else 能解决的问题？
- 抽象是否在第一次出现重复之前就建立了？

**封装**
- getter/setter 是否只是转发字段？有没有加校验、转换或副作用？
- 包装类是否只调用一次内部方法、没有添加任何行为？
- 是否存在「为了以后可能换实现」而引入的适配层，而当前只有一种实现？

**配置**
- 配置项是否只有一个取值？是否所有调用处都传同一个值？
- 是否有永远不会被设为 false 的开关、永远不会被改的常量参数？

**依赖**
- 新增依赖是否为了一个几十行能写完的功能？
- 依赖是否只是为了省事，而它带来的 API 面、升级负担、安全面大于收益？

**重构**
- 改动范围是否超出任务要求？有没有顺手重命名、顺手调整目录、顺手统一风格？
- 重构是否在没有测试覆盖的情况下进行？
- 是否把行为变更混在重构里一起提交？

**错误处理**
- 是否有宽泛的 `except` / `catch` 吞掉异常？
- 是否有返回假值的 fallback，把失败变成看起来成功？
- 是否在能加 context 的边界之外处理错误？

**测试**
- 测试是否只是复述实现（断言和实现逻辑同构）？
- 是否有为了覆盖率而写的、永远不会失败的断言？

## 不算过度工程的情况

- 确实存在两个以上调用方，且它们需要不同行为。
- 规范/协议/外部 API 强制要求的结构（如必须实现的接口、必须有的配置文件）。
- 有实测数据支撑的性能优化。
- 安全边界、输入校验、日志追踪——这些即使看起来「多余」也是必要的。

## 判断方法

对每个可疑结构问三个问题：

1. 删掉它会坏什么？说不出具体场景，就是可以删。
2. 它保护的是已知需求还是假设需求？假设需求不算。
3. 它的维护成本由谁支付？如果答案是「未来的自己」，那要更严格。

## 报告格式

```
[过度工程] <文件:行号>
结构：<接口 / 抽象类 / 配置项 / 依赖 / 重构块>
证据：<只有一个调用方 / 只有一种实现 / 取值恒定 / 超出任务范围>
最小替代：<直接内联 / 删掉 / 用标准库 / 回到原状>
```
