# A. 反模板化

审查对象：回答、说明、文档、报告、任何以文字为主的交付物。

## 判定原则

一个段落的合格标准是：读者读完能多做一件事、多做一个决定，或多排除一种可能。做不到就删掉或改写。长度本身不是问题——同样长度里塞满可执行细节是合格的。

## 检查清单

**开场**
- 是否在复述问题、宣布重要性、承诺「全面/深入」？
- 第一句能不能直接换成结论或第一个可执行步骤？

**结论**
- 结尾是否只是把开头换词再说一遍？
- 是否加了用户没要的后续建议、客套、免责声明？

**分点与标题**
- 每个列表项是不是同一层级、同一粒度？有没有一项独占三行另一项三个字？
- 能写成一句话的并列项是否被拆成了列表？
- 标题是否用了「关于…」「浅谈…」这类不承载信息的名词？

**术语**
- 有没有为了显得专业而使用的抽象词，换成日常词意思不变？
- 提到的框架、模式、最佳实践是否真的用在这个任务里，还是只是装饰？

**信息密度**
- 同一事实是否在正文、列表、表格、结论里各说了一遍？
- 有没有「看似完整」的章节：有标题、有内容、但读完不知道要做什么？

**语气**
- 是否出现无依据的最高级（「最优雅」「最佳实践」「业界标准」）？
- 是否出现对话化填充（`你会发现`、`其实`、`说白了`、`值得注意的是`、`总的来说`）？
- 是否使用 `不是 X，而是 Y` 的对仗修辞来制造力度，实际是在绕圈？排障结论里两侧都是具体失败（如「不是网络故障，而是权限配置错误」）时保留。

## 不算 slop 的情况

- 用户明确要求的详细解释。
- 真实存在的多步骤流程，步骤间有先后依赖。
- 术语是领域内的准确用词，换成日常词会损失精度。
- 长文中有结构性重复（如 API 文档每个接口都要列参数），这是格式需要。

## 修复方向

先删后改。删掉不承载信息的句子，剩下的重新排序：结论在前，理由在后。不要用加小标题、改排版的方式「压缩」内容——那只是把 slop 重新排列。

## 报告格式

```
[模板化] <文件:行号 或 段落位置>
问题：<具体是哪一句/哪个结构>
影响：<读者会因此多做什么无用功 / 少知道什么>
建议：<删掉 / 改成什么>
```
