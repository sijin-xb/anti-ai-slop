# Software engineering quality

用于实现、调试、重构、代码审查、测试和编码 Agent 工作。

## 修改前

- 读取相关实现、调用方、测试、配置和项目规范；沿调用链确认，不凭文件名推断架构。
- 尽可能复现问题，记录触发条件、错误和环境。
- 明确当前行为、目标行为、不变量、兼容约束和非目标。
- 搜索现有 helper / pattern，避免重复造轮子。

## 实施纪律

- 做最小的完整修复；保持公共接口和既有行为，除非用户授权破坏性变更。
- 抽象必须有真实收益；避免过早优化、猜测性配置、通用框架、无意义并发和宽泛异常捕获。
- 在能补充上下文或恢复的边界处理错误；不吞错、不伪造回退值、不把失败伪装成成功。
- 不添加占位实现、假数据、死配置、未使用开关或只复述实现的测试。
- 零注释：代码、脚本、测试与命令示例不写注释或 docstring；可读性靠命名、结构和测试承载，说明写进 README、提交信息或 --help。
- 提交信息用英文。
- 版本号跟随用户的发布节奏，何时递增由用户决定；未经要求不自行递增版本号或打 tag。
- 遵循仓库命名、模块边界、依赖和格式习惯。
- 除非正确性、安全性或集成要求，不顺手重构邻近代码。

## 验证

1. 先运行最窄相关测试，再按风险扩大验证范围。
2. 为已报告故障和关键边界补回归测试。
3. 检查 diff：无无关修改、误删行为、生成噪声、调试残留或意外密钥。
4. UI 修改必须检查渲染结果和相关视口/状态；构建通过不等于视觉正确。
5. 性能结论必须在可比条件下测量。
6. 报告准确的命令、结果和未覆盖范围。

## Agent 执行约定

- 以仓库真实状态为准，不假设工作区干净或分支固定。
- 保留用户已有修改；不得为了方便而 reset、覆盖或丢弃无关工作。
- 只有在有助于协调风险和范围时才给简短计划；不输出私有推理或逐条工具播报。
- 用户要求修复时，获准范围内应继续实施和验证，不要只停留在诊断。
- 阻塞时提供具体证据、影响和最小可行的部分结果。
- 完成前检查最终 diff 是否符合行为要求。

## Review 优先级

正确性/数据丢失 → 安全与信任边界 → 兼容性 → 并发与资源生命周期 → 错误处理 → 可维护性 → 风格。报告可操作问题，包含文件/符号/行号、触发条件和影响；不要为了显得全面而编造问题。
