# 文档质量

用于 README、安装/使用指南、API 参考、设计文档、架构文档、变更日志和长期维护的技术说明。

主 SKILL.md 第 3 节的中文文档硬纪律优先级高于本文件。本文件提供执行细节和骨架索引。

## 通用要求

- 面向明确读者和真实任务，优先提供可执行、可决策、可排障的信息。
- 直接从项目身份或可操作结果开始，不写目的声明。
- 描述已实现行为；命令、默认值、参数、路径和 API 形状必须核对真实实现或权威来源（流程见下节）。
- 修改既有文档前先溯源：确认它用什么流程产出、当前是否已通过本 skill 的检查。改前已合格而仍要改的，写明依据——规则变化（如预算收紧）还是主动取舍（如去重）；两者都要在改后重新过检，并保留改前通过的证据。
- 术语稳定；保留必要的限制、失败模式、迁移影响和回滚信息。
- 优先最小可运行示例；占位符必须标明且只用于确实需要替换的值。
- 删除没有读者价值的章节，不为了完整而填满模板。

## 事实核对与多语言镜像

主 SKILL.md 第 5 节是判据，这里是操作流程。文档与代码同树交付，文档里的每个操作性声明都要能在同树里找到出处。

**声明提取与核对**

1. 通读文档，标出全部操作性声明：命令、动词、旗标、默认值、数量、路径、配置键、行为保证（「绝不执行」「保留 N 份」）。
2. 逐条对照本树实现，记录 `file:line` 或实际命令输出。能跑的安全命令直接跑（`--help`、`list` 类只读命令）；跑不了的做静态核对。
3. 双向补漏：读 CLI 派发表 / argparse 注册 / 命令 usage 字符串，与文档命令表逐行比对。退出码与错误路径按实现枚举，不凭示例推断。已退役命令的声明要用代码验证「真的不再解析」，而不是凭记忆标记。
4. 计数类声明用脚本产生：`ls plugins/ | wc -l`、`grep -c`。改代码后重新数，不沿用旧数。
5. 对不上时改文档或改代码，二选一解决；「无法本地核对」（依赖上游版本、特定硬件）的声明写明适用范围，降级为待验证，不写成确定性结论。

**移植文档时**

从上游、旧版本、他人分支拿来的文档段落，按上述流程对本树全部重核。源树的实现、版本号、命令面、插件数都不自动成立。两棵树功能不同步时，明确写出哪个版本/分支适用。

**多语言镜像**

- 同一文档的语言对逐项比对：标题结构、表格行、正文中的数字、命令与旗标、列表成员。散文措辞自由，事实不许分叉。
- 改事实先同时改两个语言版本，再跑 `--pair` 复核机械项。`--pair` 只比正文；围栏与行内代码不参与，所以目录树注释里的计数、代码块里的示例数字仍靠上面的声明核对流程（`ls | wc -l`、`grep -c`）覆盖。
- 术语跨语言对齐：同一概念在每个语言里各固定一个词，且与代码中 user-facing 字符串（usage、报错、TUI 文案）对应。

**对照审查**

fork 与上游、新旧版本的文档 diff 审查逐 hunk 进行。每个差异用当前代码树裁决，采纳符合实现的一侧。裁决不了的（运行时行为、未同步的分支）标注待验证，不凭文风或新旧取舍。

**核对记录**

```
[事实核对] <文档:行>
声明：<原文>
核对：<file:line 或 命令 + 关键输出>
结果：<一致 / 不一致已改 / 无法本地核对→已标注适用版本>
```

## 极简文风

黑名单和预算只防错，这里是正向目标。实证锚点是 torvalds/linux、rust-lang/rust、golang/go 三份 README 的共性。

三者都在 40 到 130 行之间，零 emoji、零徽章、零感叹号，唯一的例外是给新来者的一句欢迎。正文是索引和分流，不是百科。

- **第一句即定义。** 开篇一句说清「是什么、给谁用」，不铺垫动机、不写开场白。
- **祈使句优先。** 读者要做的动作用祈使句写（`Run`、`Edit`、`See`），不用「用户可以」「你可以」包一层。
- **链接驱动分流。** 正文只承载 80% 场景和入口命令；长尾、原理、历史外链到对应文档。多讲一个主题，读者就多一步才碰到可复制的命令。
- **装饰归零。** emoji、感叹号、徽章、截图默认一个都不放；徽章只允许真实维护的 CI 或发布，一行。唯一例外：面向新用户的一句欢迎可以带一个感叹号。
- **示例零注释。** 命令示例不放行内注释；预期输出写成示例下方的一句散文。
- **形容词绑定事实。** 定位声明（Go 第一句的 simple / reliable / efficient）允许出现在第一句；其余形容词要么带数字或边界，要么删。
- **短句密度。** 一句一个信息点。两个信息点不共用一句；能用表格或代码块的不用散文。

## 中文文档执行细节

主节已给出预算表和句式黑名单，这里补充执行方式。

**预算溢出处理**：删低价值内容，不是改格式。删的顺序是：先删无信息段落，再删重复表述，再删可外链的长尾细节，最后才考虑缩短单句。表格、代码块、参数映射清单不算正文段落，不受单段 4 行限制；改成表格是改形式，不是删内容。

**句子超长**：拆成多个信息点，各自独立成句。不要用逗号硬连，也不要截断语义。

**段落超长**：一段只表达一个信息点。同一信息点内的多个方面用列表或表格。

**小节超长**：每个小节只回答一个问题。第二个问题另起小节或移出。

**标题层级**：超过 3 层说明结构没收敛，合并中间层或把细节移到独立文档。

## README 默认顺序

1. 项目名和具体的一句话说明。
2. 徽章（可选：仅用于真实维护的 CI 或包发布，最多一行）。
3. 安装与最短可运行示例。
4. 非默认配置。
5. 常见工作流和示例。
6. 已知限制与排障（确有必要时）。
7. 许可证 / 贡献信息（确有必要时）。

正文短时不加目录。非 GUI 项目不加截图。路线图、致谢、star 历史、FAQ 默认不加。

完整骨架见 `references/readme-skeleton.md`。

## 其他文档类型

| 类型 | 重点 |
|---|---|
| 设计文档 | 问题与现状 → 目标/非目标 → 方案 → 取舍 → 风险与回滚 |
| API 文档 | 签名、参数（类型/必填/默认值）、真实响应结构、错误条件、可运行示例 |
| 使用指南 | 按任务组织；每节含场景、前置条件、操作、预期结果、故障恢复 |
| 变更日志 | 只记用户可感知变化；没有测量依据不写「性能大幅提升」「全面优化」 |

完整骨架见 `references/doc-skeletons.md`。

## 编辑检查

逐段问：读者因此能做什么、知道什么或决定什么？若没有新增价值，删除或改写。保留安装、最小示例、限制和维护所需信息。
