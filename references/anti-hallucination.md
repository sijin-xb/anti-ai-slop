# C. 反幻觉

审查对象：所有交付物。这是五个维度里唯一不允许「看起来合理」的一项。

## 判定原则

每条陈述要么有来源，要么标明是假设。中间地带不存在。读起来顺、符合常识、像是真的，都不是证据。

## 分类

**事实来源等级**（报告里必须区分）

| 等级 | 含义 | 写法 |
|---|---|---|
| 实测 | 我跑过、看过输出 | 附命令和真实输出 |
| 源码 | 我在代码里读到 | 附 `file:line` |
| 用户提供 | 用户在对话里给的 | 标注来源 |
| 外部权威 | 官方文档、规范 | 附链接或版本 |
| 假设 | 我推断的 | 明确写「假设」 |

## 检查清单

**API 与库**
- 函数签名、参数名、返回类型是否核对过实际版本？
- 是否存在「我记得这个库有个方法」但没验证的调用？
- 默认值、必填项、错误码是否来自文档而不是推测？

**文档中的操作性声明**
- 每条命令、旗标、默认值、数量、路径是否对照**同树**代码核验过（`file:line`）？
- 有没有只对照了别的来源——上游树、旧版本、训练记忆——就当成当前树的事实？
- 代码里用户可见的动词、旗标、行为，文档是否漏记？（读派发表比对命令表，双向查）
- 多语言版本之间的数字、命令、计数是否一致？
- 计数声明是用脚本数出来的，还是凭印象写的？

**测试与验证**
- 有没有声称「测试通过」但没实际运行？
- 有没有把「类型检查通过」写成「功能正确」？
- 有没有省略失败的部分，只报告成功的部分？
- 有没有把「没跑」写成「看起来正常」？

**数据与数字**
- 性能数字是否有测量依据？测的是什么环境？
- 百分比、基准、排名是否有来源？
- 有没有把示例数据写成真实数据？

**引用**
- 链接、论文、文档版本是否真实存在？
- 有没有编造作者、标题、日期？

**UI 与视觉**
- 界面里的数字、标签、用户信息是否来自提供的数据？
- 有没有为了让界面丰满而补的内容？
- 有没有虚构的产品能力、状态、徽章？

**补全**
- 用户没说的地方，是否擅自补成了确定值？
- 缺失的信息是否用「合理猜测」填满，而没有标记？

## 高风险场景

这些场景里幻觉最容易发生且最难发现：

1. **训练数据里存在但已变更的 API。** 版本差异会让人自信地写错。
2. **本地项目的结构。** 没读文件就描述目录、模块、配置。
3. **运行结果。** 没跑就说跑过了，或者跑了一部分说全跑完了。
4. **数字。** 没有测量就说「快 3 倍」「减少 80%」。
5. **UI 内容。** 没有数据源就生成看起来真实的列表、图表、用户名。
6. **移植的文档。** 上游或旧版本的文档段落拿到本树用：命令在源树存在不代表本树存在；反向漏记本树新增的动词同样发生。

## 修复方向

不能补证据时，唯一正确的做法是把陈述降级为假设或删除。不要用更长的解释来掩盖缺失的证据。

## 报告格式

```
[幻觉] <文件:行号 或 输出位置>
陈述：<原文>
问题：<无来源 / 与实测不符 / 版本不匹配 / 编造>
证据状态：<实测为 X / 无法验证 / 与文档冲突>
处理：<改为假设 / 删除 / 补充验证命令>
```
